# MVP 개발 순서 / 첫 번째 현실적인 버전 / 최종 권장안

## 18. MVP 개발 순서

### 1단계: 텔레그램 대화와 상품 추천

- Telegram Bot 생성
- 허용 사용자 제한
- 자연어 조건 구조화
- 검색 결과 표시
- 구매 확정 버튼 구현
- 실제 결제는 하지 않음

### 2단계: Playwright 주문 미리보기

- 전용 브라우저 프로필 생성
- 최초 수동 로그인
- 상품 페이지 접근
- 옵션 선택
- 주문서 진입
- 가격·배송지·수량 읽기
- 결제 버튼은 누르지 않음

### 3단계: 안전한 결제

- 정책 엔진
- 주문 상태 머신
- 일회용 승인 토큰
- 단일 구매 워커
- 최종 재검증
- 결제 버튼 한 번 클릭
- 주문번호 확인

### 4단계: HTTP 조회 최적화

- 검색 및 상세 조회 요청 관찰
- 안정적인 읽기 요청만 어댑터로 구현
- 실패 시 Browser 조회
- 캐시 및 요청 제한 추가

### 5단계: 복구와 운영

- 주문내역 대조
- UNKNOWN 상태 처리
- 추가 인증 흐름
- 비상 정지
- 구매 감사 로그
- 선택자 변경 감지

> **진행 상황**은 프로젝트 루트 `CLAUDE.md`의 "구현 단계" 절에 반영한다 (이 문서 자체는 원래 설계
> 그대로 유지하고, 실제 완료 여부는 CLAUDE.md에서 추적).

## 19. 첫 번째 현실적인 버전

초기 버전은 아래 범위가 적절하다.

```text
지원:
- 개인 사용자 1명
- 개인 텔레그램 채팅
- 수량 1~3개
- 주문당 최대 10만 원
- 허용된 카테고리만
- 일반 단건 구매
- 가격 변경 시 재승인
- 결제 후 주문번호 확인

차단:
- 정기배송
- 상품권 및 현금성 상품
- 해외직구
- 성인 인증 상품
- 추가 인증이 필요한 구매
- 여러 판매자 상품을 한 번에 결제
- 자동 취소·반품
```

## 20. 최종 권장안

```text
Frontend
- Telegram Bot

Agent Layer
- 요구사항 파악
- 추가 질문
- 상품 비교와 추천

Tool Layer
- MCP Server
- Shopping Service
- Policy Engine

Execution Layer
- HTTP Adapter: 검색·조회 우선
- Playwright Adapter: 주문·결제 중심

Persistence
- SQLite
- 구매 상태와 감사 로그

Security
- 로컬 전용 쿠팡 프로필
- 사용자 ID 제한
- 일회용 승인
- 금액 한도
- 중복 결제 방지
```

가장 중요한 설계 결정은 다음 세 가지다.

1. **LLM이 결제 버튼을 자유롭게 조작하지 않도록 한다.**
2. **최종 구매는 저장된 주문 스냅샷과 정책 엔진을 통과한 경우에만 수행한다.**
3. **결제 결과가 모호하면 절대 자동 재시도하지 않는다.**

이 구조라면 텔레그램에서 자연어로 상품을 요청하고, 에이전트가 조건을 구체화한 뒤, 사용자의 명시적인 승인으로 쿠팡 결제까지 수행하는 개인용 쇼핑 에이전트를 단계적으로 구현할 수 있다.
